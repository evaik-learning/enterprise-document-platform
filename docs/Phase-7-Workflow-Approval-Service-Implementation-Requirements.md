- Workflow definitions

- State transitions
- Transition guards/conditions
- Workflow instances
- State-machine execution
- Sequential approvals
- Parallel approvals
- Approval assignment

- Multi-tenant organization isolation
- RBAC authorization
- Observability
- Reliable asynchronous processing

The implementation must be production-oriented and extensible.

# 2. Business Goal

A document generated by the Document Service may require a business workflow.

Example:

```text
Document Generated
       |
       v
Workflow Started
       |
       v
Draft
       |
       v
Manager Review
       |
       v
Finance Approval
       |
       v
Director Approval
       |
       v
Completed
```

A rejected document may follow another route:

```text
Finance Approval
       |
       +---- Approved ----> Director Approval
       |
       +---- Rejected ----> Revision Required
                              |
                              v
                         Manager Review
```

The workflow engine must determine what state the workflow is in, what transitions are legal, who can execute them, and what happens after the transition.

---

# 3. Core Design Principle

The engine must be based on the following model:

```text
Workflow Definition
        |
        +-- Workflow Version
                |
                +-- States
                |
                +-- Transitions
                |
                +-- Guards / Conditions
                |
                +-- Assignment Rules
                |
                +-- SLA Configuration

Workflow Definition
        |
        v
Workflow Instance
        |
        +-- Current State
        +-- Variables
        +-- Active Tasks
        +-- History
        +-- Version Snapshot
        +-- Correlation ID
```

A workflow instance must execute against an immutable workflow version.

Existing instances must NEVER change behavior because a newer workflow version is published.

Rules:

1. Draft versions can be modified.
2. Published versions cannot be structurally modified.
3. A published version can be retired.
4. New instances use the active published version.
5. Existing instances continue using their original version.

# 12. Initial and Final State Rules

Every published workflow must have:

- Exactly one Start state.
- At least one End state.
- At least one executable path from Start to End.
- No orphan state unless explicitly allowed by validation rules.
- Every transition must reference valid states.

The validator must detect:

```text
Missing Start
Multiple Start
Missing End
Invalid transition
Duplicate state key
Duplicate transition key
Unreachable state
Dead-end non-final state
Circular path without valid exit
```

Cycles are allowed only when there is a valid transition path out of the cycle.

Example:

```text
RevisionRequired
      |
      v
ManagerReview
      |
      +---- Rejected ---> RevisionRequired
      |
      +---- Approved ---> FinanceApproval
```

# 14. State Machine Rules

The engine must enforce:

```text
Current State
      |
      v
Find transition
      |
      +-- Not found --> InvalidTransition
      |
      v
Validate actor
      |
      v
Validate state
      |
      v
Evaluate guard
      |
      +-- false --> TransitionNotAllowed
      |
      v
Execute transition
      |
      v
Persist state
      |
      v
Create history
      |
      v
Publish event
```

# 21. Approval Policy

For parallel approvals:

```text
ALL
ANY
```

Example:

```text

Finance Approval
Security Approval
```

```text
ALL
```

```text
ANY
```

requires one approval.

Remaining tasks should be cancelled when ANY completes.

# 23. Parallel Approval

Example:

```text
              +--> Legal
              |

              |
```

```text

                |
                v

```

```text

Security   Pending

      |
      v

```

# 24. Approval Authorization

An approval may be executed only if:

```text
Task.Status == Pending
AND
Task belongs to organization
AND
Actor is authorized
AND
Workflow is active/running
AND
Current workflow state matches task state
```

For role-based assignment:

```text
Actor must have required role.
```

For direct assignment:

```text
Actor.UserId == AssignedUserId
```

Never trust client-provided authorization fields.

# 26. Rejection Routing

Reject must be represented as a workflow transition.

Example:

```text
FinanceApproval
       |
       +---- approve --> DirectorApproval
       |
       +---- reject ---> RevisionRequired
```

It must use the same transition engine.

# 27. Cancellation

A workflow can be cancelled if:

```text
Pending
Running
WaitingForApproval
Suspended
```

Cancellation must:

1. Validate actor permission.
2. Change instance status.
3. Cancel active tasks.
4. Record history.
5. Publish WorkflowCancelled event.
6. Trigger document/audit integration.

A completed workflow cannot be cancelled unless a future feature explicitly supports reversal.

# 30. State Transition Atomicity

A transition must be atomic from the application's perspective.

The following must not happen independently:

```text
State updated
History missing
Approval missing
Event missing
```

Use a transactional design with an Outbox pattern.

Recommended:

```text
DB Transaction
   |
   +-- Update workflow instance
   +-- Update tasks
   +-- Insert history
   +-- Insert outbox event
   |
   COMMIT
```

A background publisher sends the outbox event.

---

# 31. Optimistic Concurrency

Workflow instances and approval tasks must use optimistic concurrency.

Use SQL Server rowversion where compatible with repository conventions.

Example:

```text
WorkflowInstance.RowVersion
ApprovalTask.RowVersion
```

If two users attempt to approve simultaneously:

```text
Request A -> succeeds
Request B -> concurrency conflict
```

Request B must not advance the workflow a second time.

---

# 32. Idempotency

All externally callable state-changing APIs must support idempotency.

Recommended header:

```http
Idempotency-Key: <unique-key>
```

Store:

```text
IdempotencyRecord
-----------------
Id
OrganizationId
Key
RequestHash
ResponseStatus
ResponseBody
CreatedAt
ExpiresAt
```

If the same key is reused with a different request body:

```text
409 Conflict
```

If repeated with the same request:

```text
Return original result
```

# 38. Workflow Validation Engine

Implement a dedicated validator.

Checks:

### Structural

- One start
- At least one end
- Valid state references
- Valid transition references
- Unique keys

### Reachability

- Every executable state reachable from start
- Every non-final state has outgoing transition

### Transition correctness

- From-state and to-state exist
- No self-loop unless explicitly allowed
- Transition key unique

### Approval

- Approval state has assignment configuration
- Parallel approval has valid policy
- ALL/ANY is valid

### Version

- Published version immutable

# 67. State Transition Algorithm

Implement approximately:

```text
1. Load workflow instance with concurrency token.
2. Verify organization.
3. Verify instance status allows transitions.
4. Resolve current state.
5. Resolve requested transition.
6. Verify transition.FromState == current state.
7. Verify actor authorization.
8. Load workflow variables.
9. Evaluate guard.
10. Execute state-specific behavior.
11. Update current state.
12. Create state instance/history.
13. Create/cancel approval tasks.
14. Determine next runtime status.
15. Add domain/integration events to outbox.
16. Commit transaction.
17. Return result.
```

Do not skip steps 6–9.

# 70. Approval Completion Algorithm

When approval is approved:

```text
1. Load approval with concurrency token.
2. Verify Pending.
3. Verify actor.
4. Mark Approved.
5. Create ApprovalAction.
6. Evaluate approval policy.
7. If sequential:
       execute approve transition.
8. If parallel ALL:
       if all approved -> continue
       else remain waiting.
9. If parallel ANY:
       continue immediately.
10. Cancel remaining tasks if ANY policy.
11. Create history.
12. Create outbox events.
13. Commit.
```

---

# 71. Rejection Algorithm

```text
1. Validate approval.
2. Validate actor.
3. Require rejection comment.
4. Mark approval Rejected.
5. Create ApprovalAction.
6. Resolve reject transition.
7. Move workflow to configured rejection state.
8. Cancel sibling parallel tasks if applicable.
9. Create history.
10. Publish ApprovalRejected.
11. Publish WorkflowStateChanged.
12. Commit.
```

# 72. Concurrency Scenario

Two approvers act simultaneously:

```text
Approver A -> Approve
Approver B -> Approve
```

The database concurrency token must ensure:

```text
One succeeds.
One receives concurrency conflict/retry-safe response.
```

The workflow must never:

```text
create two next states
create duplicate next approval tasks
publish duplicate completion
```

Use database constraints and idempotent application logic as additional protection.

## Rule 2 — Reuse Existing Architecture

If Phase 4/5/6 already has:

```text
BaseEntity
Result
ProblemDetails
DbContext
Repository

Messaging
OrganizationContext
CurrentUser
Validation
Logging
```

reuse it.

Do not create competing implementations.

---

## Rule 3 — Do Not Couple Services

Never:

```text
Workflow -> direct SQL access to Document DB
Workflow -> direct SQL access to Identity DB
```

Use APIs/contracts/events.

---

## Rule 4 — Domain First

Implement business rules in Domain/Application.

Do not put state-machine logic inside controllers.

---

## Rule 5 — No Fake Workflow Engine

Do NOT implement:

```text
Approval table + status column + if statements
```

The implementation must have:

```text
States
Transitions
Guards
State machine
Workflow versions
Runtime instances
```

---

## Rule 6 — No Arbitrary Script Execution

Do not execute workflow definitions as C#, JavaScript, SQL, PowerShell, or other scripts.

Conditions must use a controlled evaluator.

---

## Rule 7 — Existing Instances Are Immutable Against Version Changes

Never dynamically switch a running instance to a newer workflow definition.

---

## Rule 8 — Every Mutation Must Be Auditable

State changes and approval actions must produce history.

---

## Rule 9 — Every Integration Event Must Be Reliable

Use the Outbox pattern.

---

## Rule 10 — Concurrency Is Mandatory

Do not assume only one approver will act at a time.
